# Xgold — الهوية والتنبيهات الجديدة فقط

الاسم الظاهر للموقع والرسائل الخاصة هو **Xgold**. الشعار الذهبي الجديد في `assets/xgold-mark.png` (PNG شفاف 1254×1254، مولّد لهذه الهوية) وصورته المصغرة المتجهة في `icon.svg`. الخط Cairo محلي، والثيمات الأربعة تظل باختيار المدير. يظهر الشعار أيضًا كعلامة مائية خفيفة لا تتداخل مع التفاعل أو قراءة المحتوى. تحميل الشعار متاح من لوحة المدير.

لم يتغير مصدر Gold API أو طريقة احتساب النتائج، ولا أصول الدخول أو الكوكيز أو معرّفات المشروع أو مفاتيح Vault أو روابط الدعم والدعوات. الاحتفاظ بأسماء البنية التحتية القديمة مقصود لتجنب كسر الاتصال أو جلسات الحسابات. تغيير الاسم الظاهر لا يشتري دومينًا ولا يغير اسم مستخدم البوت.

## نقطة فصل الرسائل

بعد 001–008، تطبّق `009_new_signals_only.sql` **مرة واحدة** عبر سجل migrations. تضيف `telegram_suppressed` وتضعه `true` لكل الصفقات الموجودة في لحظة الترقية. الإدخالات التالية تستخدم `false` افتراضيًا. القرار دائم لكل صفقة، وليس حدًا زمنيًا متحركًا أو مقارنة بوقت الحدث أو وجود رسالة أساسية. لذلك لا تعود صفقة قديمة إلى Telegram بعد إعادة تشغيل الخادم أو تحقق هدف جديد، حتى مع وجود رسالة منشورة لها.

تلغى فقط حالات الرسائل القديمة `pending/processing/failed` وتبقى صفوفها، بينما تُحفظ الرسائل المرسلة وأرقامها وكل الصفقات ولقطات أحداثها وتخصيصات المشتركين. يحظر trigger إدراج رسائل جديدة أو إعادة محاولة رسائل لأي صفقة صامتة، حتى من عامل أقدم. يعيد العامل فحص الصلاحية من الصفقة الحالية قبل كل طلب إرسال، ولا يثق بلقطة حدث قديمة. نفس الحماية موجودة في SQLite وتُختبر بعد إعادة فتح الملف.

## إصدار حي

1. تحقق من الوجهة وchecksums الخاصة بـ001–008 واحتفظ بنسخة احتياطية خاصة.
2. أوقف مهمتي السوق وTelegram مؤقتًا، وانتظر انتهاء العمال وطلبات HTTP الجارية قبل التفعيل. لا تُنشئ صفقات اختبار حقيقية.
3. في معاملة واحدة مقفلة، طبّق 009 وسجل checksum. تحقق من حفظ التاريخ والحصص والرسائل المرسلة، ومن أن الرسائل القديمة غير المرسلة صارت ملغاة فقط.
4. انشر النسخة المتوافقة، وافحص `/api/health` وإصدار النشر والواجهة، ثم استأنف المهمتين بنفس إعداداتهما السابقة. لا تعاود تنفيذ UPDATE الشامل عند كل نشر، ولا تحذف migration لإعادة تنفيذه.
5. تغيير اسم البوت ووصفه ممكن عبر Bot API. تغيير اسم الجروب وصورته يحتاج `can_change_info`؛ هذه الصلاحية **غير ممنوحة عمدًا** ضمن سياسة الجروب الحالية، فيغيرهما المالك من حسابه. لا تُمنح صلاحيات إضافة أو إخراج الأعضاء أو تعديل الجروب تلقائيًا، ولا تُرسل إعلانات أو رسائل صفقات قديمة لتجربة الهوية.

الاختبارات تغطي PostgreSQL الفعلي عبر PGlite، ترقية وإعادة تشغيل SQLite، وحماية عامل Supabase من أحداث قديمة حتى عند وجود رسالة أساسية، بالإضافة إلى إرسال وردود الصفقات الجديدة.
