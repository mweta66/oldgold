# مستويات السوق — النسخة v3

هذه قواعد تحليل فني محددة قابلة للاختبار، وليست ادعاءً بدراسة كورسات بعينها أو دليلًا على الربحية. لا تغيّر نتائج أو مستويات الصفقات القديمة ولا تنشئ تاريخًا افتراضيًا. المصدر الحالي **Gold API**؛ ليست هذه بيانات MT5 أو TradingView، ولا أوامر تنفيذ لدى وسيط.

## الدخول والمستويات

- يظل اتجاه M15 مع EMA8/EMA21، والدخول بعد إغلاق دقيقة تتجاوز أعلى/أدنى آخر20 دقيقة، مع سلامة آخر5 ساعات وتهيئة حتى8 ساعات. لا تُستخدم الدقيقة الحالية غير المكتملة لتأكيد كسر أو قمة/قاع.
- القمة/القاع من آخر سعر **مرصود** لكل دقيقة مكتملة. يلزم وجود دقيقتين مكتملتين قبله وبعده، دون فجوة محلية؛ وقت التأكيد منفصل عن وقت القمة. يُستبعد المستوى الذي كُسر بعد تأكيده.
- الوقف خلف أحدث قاع مناسب للشراء، أو أحدث قمة مناسبة للبيع، خلال آخر90 دقيقة، مضافًا إليه هامش متغير: نصف متوسط التغير المطلق في آخر20 دقيقة، بحد تقني أدنى0.02 لحجم دقة التسعير. هذا **ليس ATR** ولا نطاق OHLC؛ لا تتوفر هنا شموع وسيط كاملة.
- الأهداف قبل أقرب مستويات مقاومة للشراء أو دعم للبيع خلال السجل المرصود، مع نفس هامش التقلب. تعرض الإشارة1–3 أهداف حسب المستويات الموجودة، ولا تُختلق ثلاثة أهداف ولا تستخدم مضاعفات ثابتة لمسافة الوقف.
- إذا لم توجد مستويات مؤكدة مناسبة، أو كان أقرب هدف لا يحقق عائدًا مرجعيًا إلى المخاطرة لا يقل عن1.2، تُترك الفرصة. لا يُتخطى حاجز قريب لاختيار هدف أبعد وتحسين النسبة ظاهريًا. يرفض المحرك وقفًا أبعد من1% من المرجع، وهو حد أهلية لا مسافة وقف ثابتة.

تُحفظ أسباب الاختيار في `market_levels`: وقت وسعر القمة/القاع وتأكيدها، هامش التقلب، ومستويات الأهداف الأصلية. تعرض بطاقة الصفقة «لماذا هذه الأهداف وهذا الوقف؟». غياب البيانات القديمة يظل غيابًا؛ لا يُملأ بسبب مفترض. يعيد PostgreSQL اشتقاق المستويات من الأسعار المخزنة قبل قبول النشر، ولا يثق بمستويات العامل وحدها.

## الرصد السحابي

تضيف012 جامعًا اختياريًا سحابيًا افتراضيًا **معطّلًا**. بعد فحص مصدر حي وتفعيل الجدولة، تستخدم مهمة Supabase واحدة كل3 ثوانٍ `pg_net` لجمع المصدر دون جهاز شخصي. يتم منع الطلبات المتزامنة، واحترام الانتظار عند الخطأ و429. يظل وقت المصدر الحقيقي محفوظًا، والتكرار لا يخلق سعرًا أو فرصة.

حساب المؤشرات وإشارات v3 ومتابعة TP/SL يتم داخل PostgreSQL، لتجنب نقل8 ساعات من الأسعار أو تشغيل Vercel كل3 ثوانٍ. يتطابق المخطط السحابي مع العامل JavaScript في اختبارات مراحل M15 الخمس عشرة. يستدعى عامل Telegram المحمي فقط عند وجود رسالة مستحقة؛ مهمة إعادة المحاولة المستقلة كل دقيقة تبقى كاحتياط. خصوصية الجروب والصلاحيات والحصص والرد على رسالة الصفقة الأصلية وقواعد الإيقاف كلها محفوظة.

«كل3 ثوانٍ» هو **جدول فحص تقريبي** وليس ضمان تحديث السعر أو تنفيذ وقف أو وصول Telegram خلال3 ثوانٍ. قد تُفقد حركة بين القراءات، ويظل الانقطاع لأكثر90 ثانية نتيجة غير محسومة وفق السياسة السابقة. بعد SL لا تُسجل أهداف جديدة على الصفقة.

تظل الواجهة تستطلع حالتها كل15 ثانية عند فتحها، مستقلة عن جمع السوق كل3 ثوانٍ. حدود الاستخدام المجاني للمضيف وقاعدة البيانات تظل سارية؛ لا يُشترى اشتراك أو سعة إضافية تلقائيًا.

بعد013 أُلغي حد النسبة التراكمية بطلب المالك: لا يمنع عداد الخسائر القديم تحليل فرصة أو نشرها، سواء تجاوز10 أو أكثر. تبقى قيم `loss_used` و`risk_reference_pct` التاريخية وحساباتها القديمة للتوافق والتدقيق فقط؛ ليست سياسة رأس مال أو حدًا مفروضًا على النشر. لا تُصفّر أو تُعدّل النتائج والحصص السابقة. تُرجع حالة المحرك `cumulativeRiskLimitEnabled:false`، ولا تعرض الواجهة أو رسائل الخاص نسبة مخصصة للمخاطرة. تبقى مستويات SL/TP، صلاحية البيانات، اكتمال التحليل، صفقة نشطة واحدة، الانتظار بعد الإغلاق وأزرار إيقاف المدير كما كانت. لا يُفرض عدد إشارات ولا تُنشر فرصة دون تحقق شروطها، ولا توجد حماية لخسارة حساب الوسيط.

توثيق المصدر الذي روجع2026-10-24: [الواجهة](https://gold-api.com/docs)، [التسعير المجاني](https://gold-api.com/pricing)، [الشروط](https://gold-api.com/terms). الواجهة المجانية تسمح بطلبات السعر، بينما الشروط تمنع الطلبات المتعددة في الثانية. رُصد `Cache-Control: public, max-age=3`؛ لذلك لا يُوعَد بسعر مستقل كل ثانية. لا تُضاف خدمة مدفوعة أو نموذج ذكاء اصطناعي إلى المحرك.

## ترقية آمنة

طبّق010–012 بعد001–009 مرة واحدة، مع نسخة احتياطية ومراجعة checksums وإيقاف العمال وانتظار انتهائهم. لا تُفعّل المجمع أثناء تطبيق SQL أو قبل نشر العامل المتوافق. يلزم وجود Vault origin/cron secret الحاليين وإعداد `xgold_telegram_group_id` للوجهة الخاصة المتحققة، ثم تحويل مهمة السوق القائمة إلى `select public.wg_market_poll();` كل `3 seconds`. لا تغير تفعيل نشر الإشارات أو ميزانية الخسارة أو حسابات المشتركين ضمن التحويل.

تُطبق013 بعد012 فقط، دون تعديل الملفات المسجلة: توقف مهمة السوق وتنتظر انتهاء عاملها، وتحفظ نسخة من الدوال والسجل والحصص والعداد القديم. الترقية تستبدل مساري النشر والتحليل السحابي وتزيل شرط النسبة فقط، وتنتظر قراءة حديثة بدل إعلان فرصة جاهزة. لا تنشئ صفقة أو ترسل تحديثًا قديمًا أثناء SQL. فحص الحالة والصحة يتأكد من دالة السياسة الخاصة؛ فلا تُعلن سياسة غير مطابقة لقاعدة البيانات. بعد نشر النسخة المتوافقة تستأنف نفس مهمة3 ثوانٍ وتتحقق من سبب المحرك والسعر وطابور Telegram. حدود محاكاة البحث التاريخي المعزولة لا تتحكم في النشر الحي ولم تُغيّر نتائجها بأثر رجعي.

يُحتفظ بسجل الأسعار7 أيام كما كان؛ تنظّف الوظيفة فقط سجلات تشغيل جامعها الجديدة الأقدم7 أيام، ولا تحذف صفقات أو نتائج أو سجلات Cron التي تسبق تفعيلها. عند فشل فحص المصدر أو الجدولة لا تُعلن3 ثوانٍ كميزة فعالة. SQLite يدعم الصفقات اليدوية ومفتاح Telegram؛ الجامع السحابي خاص بمشروع Supabase.
