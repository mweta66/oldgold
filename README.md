# WetaGold

رسائل البوت تميّز الشراء بـ🟢 📈 والبيع بـ🔴 📉، والأهداف بـ✅ والوقف بـ❌. كل تحديث يرد على رسالة الصفقة نفسها، مع حفظ معرّفها لكل محادثة بعد إعادة التشغيل. يتطلب ذلك migration `008_telegram_replies.sql` بعد 001–007؛ راجع [الرسائل القديمة وإعادة المحاولة](docs/TELEGRAM.md#ردود-الأهداف-والوقف-على-رسالة-الصفقة). لا يغيّر التعديل مصدر الأسعار أو طريقة توليد الإشارات.

منصة عربية لنشر ومتابعة إشارات الذهب، بلوجو ذهبي شفاف وعلامة مائية خافتة وخط Cairo محلي. الإشارات والشارت بعد تسجيل الدخول فقط. المدير الوحيد ينشئ حسابات المشتركين ويحدد الحصة ونهاية التفعيل ويختار ثيم الموقع: ذهبي، أزرق، زمردي أو فاتح.

النشر الجديد يربط **Vercel مباشرةً بـ Supabase Auth وPostgreSQL**؛ لا يحتاج خادم Backend منفصلًا أو SQLite على Vercel. المستودع لا يتضمن مشروع Supabase فعليًا أو مفاتيح أو حسابات إنتاج جاهزة. نجاح البناء لا يعني تفعيل تسجيل الدخول.

## التفعيل والتشغيل

التفاصيل: [دليل Supabase](docs/SUPABASE.md).

لتشغيل محرك الذهب المجاني طبّق أيضًا `005_gold_market.sql` ثم `006_rolling_market_window.sql` بعد 001–004، ثم اتبع [دليل المحرك](docs/GOLD-MARKET.md). يفحص المحرك آخر خمس ساعات ويحفظ بياناته بعد الانقطاع؛ لا يعيد كتابة تاريخ اليومين الماضيين، ولا ينشر قبل سلامة التغطية وتهيئة الاتجاه والتحقق من اتصال المصدر.

تطبيق `007_optional_manual_reference.sql` بعد 001–006 يجعل السعر المرجعي ووقت السعر اختياريين في النشر اليدوي، كل حقل مستقل عن الآخر. غيابهما لا يمنع تخصيص الإشارة أو إرسال الجروب؛ يُحفظ الغياب كـ`null` دون نسخ سعر الدخول أو وقت النشر كمرجع وهمي. تظل مراجع المحرك الآلي مطلوبة ولا تتغير.

إذا حُفظت مفاتيح الإدارة في GitHub Actions بدل إعدادات البيئة، راجع [فحص اتصالات النشر الآمن](docs/CLOUD-ACTIVATION.md). الفحص لا ينشئ موارد ولا يعلن أن الموقع جاهز للإنتاج.

1. أنشئ مشروع Supabase وشغّل migrations [001](supabase/migrations/001_wetagold.sql) ثم [002](supabase/migrations/002_trade_history.sql) ثم [003 لتنبيهات Telegram](supabase/migrations/003_telegram_events.sql) ثم [004 للأهداف المتعددة](supabase/migrations/004_multiple_targets.sql) بالترتيب. طبّق الملفات غير المطبقة فقط دون مسح البيانات؛ راجع [خطة ترقية الأهداف والعمال](docs/MULTIPLE-TARGETS.md) قبل ترقية بوت حي.
2. أضف `SUPABASE_URL` و`SUPABASE_ANON_KEY` و`SUPABASE_SERVICE_ROLE_KEY` في بيئة **الخادم** في Vercel، و`PUBLIC_ORIGIN` لدومين الموقع النهائي و`COOKIE_SECURE=true`. لا تنشر مفاتيح في المتصفح أو Git أو المحادثة.
3. أنشئ أول مدير من بيئة موثوقة بأداة التهيئة أدناه، ثم أعد نشر الموقع. الحساب المحلي السابق لا ينتقل تلقائيًا إلى Supabase. لا تحتاج `BACKEND_ORIGIN`.
4. اختبر `/api/health` ثم تسجيل الدخول وتغيير كلمة المرور المؤقتة وإنشاء مشترك وتغيير الثيم. عند غياب الخدمة، تعرض الواجهة السبب وتعطل الدخول بدل تقديم نجاح وهمي.

استخدم Node.js **24.10 أو أحدث**. أنشئ `.env` محليًا اعتمادًا على `.env.example` واضبط مفاتيح مشروعك و`ADMIN_EMAIL` و`ADMIN_PASSWORD` بشكل سري:

```bash
npm ci
npm run supabase:bootstrap
npm start
```

الأداة ترفض استبدال المدير الموجود وتفرض تغيير كلمة المرور عند أول دخول. استخدم كلمة قوية من 12–128 حرفًا؛ كلمة التهيئة الأقصر لا تعمل إلا إذا سمحت بها سياسة Supabase. احذف كلمة التهيئة من البيئة بعد الإنشاء، ولا تضفها إلى Vercel. لا يوجد حساب افتراضي أو مسار API لإنشاء مدير ثانٍ.

الخادم المحلي على المنفذ 8000. `STORAGE_PROVIDER=supabase` يمنع الرجوع الصامت إلى حسابات SQLite عند نقص الإعدادات. صفحة `/admin` لا تمنح صلاحية؛ الدور يفحص في الخادم وقاعدة البيانات.

## حماية البيانات وحصص الإشارات

- Supabase Auth يتحقق من كلمات المرور؛ المتصفح يأخذ جلسة عشوائية HttpOnly وSameSite=Strict، لا JWT أو مفتاح خدمة. معرّف الجلسة مخزن كـ hash وينتهي بعد 12 ساعة. التعديل يحتاج Origin صحيحًا وCSRF.
- RLS مفعّل وجداول الموقع ودواله محظورة على `anon` و`authenticated`؛ الوصول من API الخادم فقط. الدور لا يؤخذ من metadata يستطيع المستخدم تعديلها.
- الحصة **إجمالي الإشارات الجديدة المخصصة للحساب**، لا عدد مرات فتح الصفحة أو حصة يومية. التخصيص والخصم وطابور Telegram في معاملة PostgreSQL واحدة. تكرار `requestId` لا يخصم مرتين.
- نفاد الحصة يمنع الإشارات التالية، وتبقى متابعة المستلم حتى انتهاء التفعيل. الحساب المنتهي/الموقوف لا يجلب إشاراته. التجديد لا يوزع إشارات قديمة ولا يصفر الاستخدام: رفع الإجمالي من 10 إلى 20 بعد استلام 8 يعني 12 متبقية.
- سجل الصفقات يعرض **كل تاريخ الحساب** في صفحات من 20 صفقة، مع فلاتر تاريخ النشر (أيام كاملة بتوقيت الحساب المختار) والحالة والاتجاه، وتوقيت النشر والفتح والإغلاق/الانتهاء. لا يوجد حد 90 يومًا أو 200 صفقة على السجل. قراءة الصفحات لا تستهلك الحصة.
- ملخص الأداء منفصل: حتى 200 إشارة ضمن 90 يومًا. الإشارة المفتوحة لا تختفي من مساحة العمل لمجرد قِدم تاريخ نشرها. نسبة النجاح من النتائج المسجلة يدويًا، وليست نتائج استراتيجية مختبرة أو نسبة كل السجل.
- أوقات الفتح والإغلاق القديمة تستعاد فقط من أحداث audit المسجلة؛ المفقود يظهر «غير مسجّل»، دون تواريخ مصطنعة. الفراغ يوضح الفرق بين عدم نشر صفقات، أو عدم تخصيصها للحساب، أو فلاتر بلا نتائج، أو فشل تحميل.
- عند عدم وجود إشارات معلقة أو مفتوحة، تعرض مساحة العمل آخر إشارة منشورة مسموحة للحساب من **كل تاريخه**، حتى لو أقدم من 90 يومًا، مع تنبيه أنها صفقة سابقة وليست توصية دخول جديدة. وقت الدخول هو `openedAt` المسجل بالثانية وبتوقيت الحساب، ولا يُستبدل بوقت النشر أو سعر الشارت. قراءة آخر صفقة لا تستهلك حصة، وفلاتر السجل لا تغيّرها.

## عناوين تسجيل الدخول على Vercel

في وضع Supabase، يقبل فحص مصدر الطلب `PUBLIC_ORIGIN` وكذلك العناوين الدقيقة التي يحددها Vercel في `VERCEL_URL` و`VERCEL_BRANCH_URL` و`VERCEL_PROJECT_PRODUCTION_URL` عند `VERCEL=1`. هذا يمنع رفض تسجيل الدخول عند فتح رابط نشر خاص بنفس المشروع بدل الرابط الأساسي. لا يوجد سماح عام لـ`*.vercel.app`، ولا اعتماد على `Host` أو `X-Forwarded-Host` لتحديد العناوين الموثوقة في Vercel، ولا تغيير لحماية CSRF أو كلمات المرور أو صلاحيات الحساب. يجب إتاحة متغيرات Vercel النظامية للنشر. لا تُضاف عناوين من مدخلات المستخدم. في الاستضافة المحلية يبقى السلوك السابق دون تغيير.

## البلد وتوقيت الحساب

يختار المشترك بلده والمنطقة الزمنية من قسم الحساب؛ البلدان متعددة التوقيت تعرض مناطقها للاختيار. يُحفظ الاختيار لكل حساب على الخادم (في `user_metadata.wetagold_display` داخل Supabase Auth، أو أعمدة محلية في SQLite)، ولا يؤثر في الدور أو الصلاحيات أو حصص الإشارات. لا توجد geolocation أو محاولة لتحديد مكان المستخدم. الافتراضي للمشترك UTC حتى اختيار بلده؛ حساب المدير ثابت على `Africa/Cairo` (توقيت مصر).

العرض في البطاقات والسجل ونهاية الاشتراك وآخر مزامنة يتبع المنطقة المختارة. الشارت خاص بالمدير فقط وبتوقيت مصر. توقيت مصر يُراعى صيفًا وشتاءً ولا يثبت عند UTC+2. فلاتر أيام السجل تتحول على الخادم إلى حدود UTC صحيحة، بما فيها أيام 23/25 ساعة. مدخلات المدير لتاريخ الانتهاء ووقت السعر تُفسّر بتوقيت مصر وتُحوّل إلى UTC؛ الأوقات المحلية غير الموجودة أو المكررة عند انتقال التوقيت الصيفي تُرفض برسالة واضحة بدل التخمين. تخزين الأحداث والأهلية والانتهاء يظل UTC دون تغيير. رسائل Telegram المشتركة تظل بتوقيت UTC المبيّن في الرسالة؛ هذا اختيار عرض للموقع، وليس إعادة كتابة للأحداث أو الرسائل السابقة.

## مختبر Bybit

أضيف مختبر بحثي للمدير لمحاكاة آخر 48 ساعة من شموع Bybit العامة، منفصل تمامًا عن الصفقات المنشورة. لا يحتاج اشتراك بيانات أو مفتاح تداول؛ يرفض البيانات غير الموثوقة ولا يستبدل الذهب بعملة ذهب مرمّزة. القواعد أولية غير معتمدة، ولم يُنجز اختبار حي ناجح أو تفعيل نشر آلي. راجع [القواعد والتكاليف والقيود وحالة الإطلاق](docs/BYBIT-RESEARCH.md). نُشرت إعدادات السماح بالاتصال سابقًا، لكن ذلك لا يلغي حظر البلد الصادر من المزود؛ طلب Publish جديد ليس حلًا له.

## استقرار الشاشة وتشخيص التشغيل

- لا يعيد التحديث غير المتغير رسم بطاقات الإشارات، وتبقى مسودة اختيار الحالة محفوظة حتى لو أضيفت إشارة أخرى. الطلب الجاري يحتفظ بقفل زر الحالة والقائمة عبر إعادة الرسم لمنع إرسال العملية مرتين.
- عند فشل تحديث السجل مؤقتًا، تبقى آخر صفحة ناجحة **لنفس الحساب والفلاتر والصفحة والتوقيت** مع تنبيه واضح أنها قديمة. تغيير الفلاتر لا يعرض نتائج قديمة كأنها نتائج الفلاتر الجديدة؛ الخروج أو فقدان الصلاحية يمسح البيانات. التحديث الجزئي لا يغيّر توقيت آخر مزامنة مكتملة.
- تصدير CSV يخص **الصفحة المعروضة فقط**، وليس كل السجل أو محاكاة آخر 48 ساعة. يتضمن UTC والتوقيت المختار، ويمنع حقن صيغ الجداول. الملف ينزله المستخدم صراحة؛ لا يخزن الموقع بيانات خاصة في localStorage أو service worker. احفظ الملف بأمان ولا ترفعه إلى مستودع عام.
- حسابات الإدارة بصفحات خادمية من 20 وبحث بالبريد، مع عدد مطابق من قاعدة البيانات؛ لا يُعتمد على قائمة Supabase قد تتوقف صامتًا عند حد الصفوف. البحث لا يفسر `%` أو `_` كحروف بدل.
- زر «فحص الخدمات» يستدعي `/api/admin/diagnostics` للمدير فقط، لفحص قراءة الجداول وواجهة إدارة Auth وإظهار آخر حالات رسائل الطابور دون أرقام محادثات أو أسرار. `release` مأخوذ فقط من SHA صالح يقدمه الخادم؛ غيابه يظهر صراحة. فحص Auth ليس اختبار كلمة مرور مستخدم.
- `/api/health` يتحقق من الجداول والأعمدة المطلوبة في migrations 001–004 ومن سجل الإعدادات، وليس جدول الإعدادات وحده. لا يثبت عمل RPC أو ربط السوق أو Cron أو وصول Telegram؛ تبقى هذه حدودًا معلنة في لوحة الفحص. طلبات Supabase لها مهلة شبكة 8 ثوان لكل طلب، وليس ضمان إكمال رحلة متعددة الطلبات في 8 ثوان.
- يحترم عامل Telegram قيمة `retry_after` الموثوقة عند تقييد الإرسال، ويخزن الموعد القادم في الطابور بدل المحاولة المبكرة. تبقى الدفعة حتى 20 والمحاولات حتى خمس، ويحتاج التوسع اختبار حمل ومتابعة الجدولة.

راجع [بوابات الإصدار والطلبات غير المكتملة](docs/RELEASE-CHECKLIST.md) قبل وصف المنتج بأنه جاهز بالكامل. دعم الأهداف المتعددة يحتاج ترقية 004 والكود المتوافق؛ لا يفعّل السوق أو MFA أو نسخ Supabase تلقائيًا.

## الشارت وحدود الإشارات

شارت TradingView الفعلي مثبت على `OANDA:XAUUSD` بفريمي دقيقة و15 دقيقة، وهو للمراجعة الشخصية للمدير وحده وبتوقيت مصر. لا يُنشأ iframe ولا طلب إلى مزود الشارت للمشترك أو الزائر، بما في ذلك بعد تبديل الحساب أو إعادة التحميل وتغيير التوقيت والثيم. المشترك يرى الإشارات المخصصة له وآخر صفقة وسجلها فقط دون رسم بياني؛ حقول الحساب والتوقيت تظل متاحة. لا يوجد سعر ثابت أو صفقات افتراضية. هذا مصدر مختلف عن Bybit وقد يختلف سعر التنفيذ عند وسيط آخر.

تنبيهات Telegram للإشارات المنشورة وتحديثاتها نصية ولا تشمل رسمًا بيانيًا، وترتبط بالطابور الدائم وفحص الجروب الخاص. إشارات OANDA اليدوية تظل حسب تسجيل المدير. محرك Gold API المنفصل يضيف توليدًا وتتبعًا آليين بعد التفعيل والتهيئة كما في [دليل محرك الذهب](docs/GOLD-MARKET.md)، مع تمييز القراءات المتقطعة عن التنفيذ وعدم استخدام شارت OANDA أو واجهة Dukascopy المحمية كمصدر له.

**الشارت ليس API لمحرك تداول.** الإشارات اليدوية يتحقق الخادم من ترتيب مستوياتها، وحداثة وقت السعر وقرب الدخول من المرجع عند إضافتهما اختياريًا فقط، دون إثبات تنفيذ. المحرك الآلي يستخدم Gold API المجاني وفق شروط الاستخدام الموضحة في [دليله](docs/GOLD-MARKET.md). لا توجد استراتيجية AI مدربة أو مثبتة الربحية أو تنفيذ صفقات. الإشارات وحدها لا تستطيع فرض حد خسارة على منصة تنفيذ خارجية.

صلاحية الدخول 15 دقيقة؛ المعلقة القديمة تنتهي تلقائيًا. المفتوحة تظل كذلك حتى يسجل المدير الهدف أو الوقف أو الإلغاء. الحد الأقصى إشارتان نشطتان. الإيقاف يمنع نشر الجديد، والمستويات المنشورة لا تعدل وتغييرات الحالات مسجلة.

## Telegram

ضع `TELEGRAM_BOT_TOKEN` و`TELEGRAM_WEBHOOK_SECRET` و`CRON_SECRET` في بيئة الخادم فقط. بعد النشر شغّل `npm run telegram:webhook` من بيئة موثوقة واضبط الجدولة كما في [الدليل](docs/SUPABASE.md#telegram-والإرسال-الدوري).

يربط المشترك البوت من حسابه برابط أحادي الاستخدام صالح لعشر دقائق ثم يضغط Start. تنبيهات النشر وتغيير الحالة تحفظ كأحداث مستقلة ولقطات ثابتة في outbox دائم، وتبدأ محاولة الإرسال عند النشر والتحديث. تصل تحديثات كل TP وSL والإلغاء والانتهاء والنتيجة غير المحسومة تلقائيًا عند تسجيلها، ولا تخصم حصة إضافية. تدعم النسخة هدفًا إلى ثلاثة أهداف ووقف SL واحدًا مع ترتيب التحديثات. في إشارات `GOLDAPI:XAUUSD` يسجل المحرك العبور المرصود آليًا، بينما تظل إشارات OANDA حسب المدير؛ لا يثبت أي منهما تنفيذًا جزئيًا أو أرباح مركز. راجع [الأهداف المتعددة](docs/MULTIPLE-TARGETS.md) و[حدود المتابعة الآلية](docs/GOLD-MARKET.md).

لا يرسل العامل دعوة دخول قديمة بعد انتهاء صلاحية الدخول؛ تحديثات النتائج تظل قابلة للإرسال 24 ساعة من تسجيلها حتى لو انتهى وقت الدخول. يحترم ترتيب الأحداث لكل محادثة ويعيد المحاولة تدريجيًا حتى خمس مرات، ثم يتدخل المدير. قد تتأخر دفعة خلف إرسال سابق؛ **جدولة كل دقيقة لازمة لبقية الدفعات وإعادة المحاولات** على Vercel.

`TELEGRAM_GROUP_CHAT_ID` لجروب إشارات **خاص يديره المالك يدويًا**. لا ينشر الموقع رابط دعوة ولا يضيف أو يخرج أحدًا. اربط Telegram الخاص بالمدير وتأكد أنه مالك الجروب؛ امنع دعوة الأعضاء العاديين، واجعل المشرفين أنت والبوت فقط، والبوت بدون صلاحيات دعوة/حظر/ترقية/تغيير معلومات. فحص الخصوصية يسبق كل دفعة إلى الجروب، مع زر فحص في الإدارة. التفاصيل في [دليل Telegram](docs/TELEGRAM.md).

الجروب يستقبل **كل الإشارات والتحديثات**؛ حصة حساب الموقع وانتهاء تفعيله لا يمنعان قراءة جروب مشترك ولا يخرجان العضو تلقائيًا. المالك يراجع العضوية ويزيل المنتهي بنفسه. الرسائل الخاصة فقط تبقى مقيدة بتفعيل الحساب والإشارات المخصصة له. المتغير القديم `TELEGRAM_ADMIN_CHAT_ID` مدعوم كاسم بديل؛ الجديد له الأولوية. لتعطيل الجروب احذف المتغيرين.

لا ندّعي exactly-once: قد تتكرر رسالة إذا قبلها Telegram ثم انقطع الرد؛ رقم الإشارة والحدث في كل رسالة يساعدان على التعرف عليها. تجهيز الكود لا ينشئ بوتًا أو جروبًا ولا يثبت إرسالًا حيًا. ترقية SQLite القديمة تحتفظ بطابورها السابق داخل `outbox_v1_backup` للاسترداد، دون حذف سجلاته أو تصفير الاستخدام.

## الاختبارات والنشر

```bash
npm run check
npm run build:static
npm test
npm run test:browser
npm run format:check
```

اختبارات PostgreSQL تشغل migration والصلاحيات والحصص والدوال فعليًا باستخدام PGlite. اختبارات API تستخدم SDK الحقيقي مع محاكاة شبكة المزود. Chromium يختبر الدخول والصلاحيات والثيمات وتباين الألوان وCairo واللوجو والموبايل وتعطل الخدمة وmanifest بكوكي معاينة. Telegram وTradingView معزولان؛ لا تثبت الاختبارات جاهزية الحسابات الخارجية أو سعر السوق. الصور في `test-results/` مستبعدة من Git. يستخدم المتصفح Chromium المحلي أو `CHROMIUM_PATH` أو تثبيت Playwright.

Vercel يبني ملفات عامة محددة في `dist/` ويشغل API بدالة الخادم. Manifest يرسل credentials لنفس المصدر وCSP يبقى `manifest-src 'self'`؛ لا نسمح بصفحة SSO كأنها manifest. المعاينات تحتاج مشروع اختبار مستقلًا؛ Telegram والجدولة يحتاجان دومين إنتاج عامًا.

النسخ والاستعادة في Supabase تعتمد خطتك وإعدادات مشروعك. لا تعد هذه النسخة بنسخ يومية مجانية أو استعادة اختبرت خارجيًا. SQLite القديم باقٍ للتطوير والاختبارات إذا غابت إعدادات Supabase و`STORAGE_PROVIDER`؛ ليس بديل الإنتاج على Vercel.
